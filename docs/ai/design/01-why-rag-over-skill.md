# 为什么用 RAG + 向量数据库，而不是 Skill

## 背景

当前系统中，钉钉知识库的查询通过 Claude Code Skill（dingtalk-docs）实现。这个 skill 的工作原理：用户提问 → 钉钉 API 关键词搜索 → 获取整篇文档 → LLM 阅读后回答。

RAG（Retrieval-Augmented Generation）是另一种方案：文档提前同步、切片、向量化存入数据库 → 用户提问 → 语义检索相关片段 → LLM 基于片段回答。

本文档记录为什么要在系统中引入 RAG + 向量数据库，而不是继续只用 Skill。

---

## 核心差异

| 维度 | Skill | RAG |
|------|-------|-----|
| 搜索方式 | 钉钉 API 关键词匹配 | 语义向量检索 + 关键词混合检索 |
| 内容粒度 | 整篇文档，可能包含大量无关内容 | 按标题层级切片，只取最相关的片段 |
| 数据源 | 实时拉取钉钉 API | 预同步到本地数据库 |
| 响应速度 | 慢（串行调用搜索 + blocks API，大文档更慢） | 快（本地检索毫秒级） |
| 语义理解 | 关键词死匹配，搜不到同义表达 | 向量距离度量语义相似度 |
| 权限控制 | 实时同步钉钉权限 | 同步时静态快照 |
| 调用方式 | 仅限 Claude Code 对话中 | REST API + SSE，任何客户端可接入 |
| 成本 | 每次查询都调钉钉 API + 传输整篇文档 token | 本地检索，只传相关片段 |

---

## 为什么 Skill 不够用

### 1. 关键词搜索的天花板

Skill 依赖钉钉 storage search API 做关键词匹配。它只能找到"包含这个词"的文档，找不到"意思相近但用词不同"的文档。

例如搜索"急停距离"，可能漏掉写了"制动距离"但意思完全相同的文档。关键词搜索没有"理解"能力。

### 2. 整篇文档粒度太粗

Skill 获取整篇文档（最多 3 篇）交给 LLM 阅读。这会带来几个问题：

- **Token 浪费**：一篇文档可能几千字，用户只关心其中一段，但整篇都送进 LLM
- **干扰噪音**：无关内容可能冲淡关键信息，降低回答质量
- **上限硬约束**：LLM context 有限，3 篇大文档可能就把窗口撑满了

### 3. 只有人工入口

Skill 只能在 Claude Code 对话中用。无法被其他系统调用，比如：

- Web 页面上的知识库问答
- 任务创建时自动检索引用的规范
- 定时批量分析

### 4. 性能不稳定

每次查询都要串行走：
```
钉钉 API 搜索 → 查缓存 → (未命中) → blocks API 获取正文 → 解析 → LLM 回答
```

大文档的 blocks API 返回大量 block，且附件（图片/视频）无法处理，每次都要通过网络拉取。

---

## 向量数据库解决了什么问题

### 1. 语义理解

向量数据库存的是文档片段的"语义向量"。搜索时比较的是"含义是否接近"，而不是"关键词是否匹配"。

- 搜"怎么停车" → 能召回写了"制动流程"的文档
- 搜"激光没数据" → 能召回写了"传感器断连排查"的文档
- 搜"节拍慢" → 能召回写了"效率优化"的文档

这是关键词搜索做不到的。

### 2. 精准定位

文档被按标题层级切成小块（每个 `##`/`###` 一节），检索时只返回最相关的 top-K 片段（默认 8 段，每段 800 token）。LLM 接收到的是精确命中用户问题的内容，而不是整篇文档。

### 3. 可编程接入

RAG 对上层暴露的是 REST API：

```
GET /ai/knowledge/chat?q=用户问题
→ SSE 流式返回回答 + 引用来源
```

任何系统都可以调用：前端页面、任务分析流程、自动化脚本。

### 4. 检索速度

本地向量检索 + FTS5 全文索引在毫秒级完成，无需网络请求钉钉 API。（当然文档的同步更新依赖定时任务，不是实时的。）

---

## 什么时候该用 Skill，什么时候该用 RAG

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 开发者临时查一份文档 | Skill | 实时、无需提前同步 |
| 查的数据刚刚才更新（几分钟内） | Skill | RAG 同步有延迟 |
| 没有权限访问的文档 | Skill | RAG 同步受限于同步时的权限 |
| 面向全公司的知识库问答 | RAG | 速度快、语义准、可网页接入 |
| 任务创建时自动引用规范 | RAG | 后端 API 可编程调用 |
| 批量分析/报表 | RAG | 不需要人工介入 |
| 在手机上/钉钉内查文档 | RAG | 通过网页或 API 暴露 |

**两者是互补关系，不是替代关系。** Skill 解决"临时、实时、高权限"的需求，RAG 解决"批量、语义、可编程"的需求。

---

## 结论

引入 RAG + 向量数据库不是因为 Skill 做得不好，而是因为 Skill 适用的场景有限：

1. **Skill 是给开发者用的**（Claude Code 对话框里）
2. **RAG 是给系统用的**（REST API、前端页面、自动化流程）

如果你今天想要：
- 开发者查文档 → Skill 更快
- 全员知识库问答 → RAG 更合适
- 自动引用规范 → 只有 RAG 能做到
- 语义搜索 → 只有 RAG 能做到
