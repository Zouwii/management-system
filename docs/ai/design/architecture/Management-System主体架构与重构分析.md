# Management-System 主体架构与重构分析

> 状态：架构现状分析稿  
> 日期：2026-08-03  
> 范围：只描述当前系统边界和重构方向，不代表已经实施重构。

## 1. 核心结论

Management-System 已经不是单一工时系统，而是多个业务域共享一个 Flask 进程、一个 React 前端外壳以及一套钉钉接入基础设施的单体应用。

当前可归纳为 **6 个主要业务域** 和 **3 个平台能力**。如果将现场问题与需求池分别计算，也可以视为 7 个业务域。

```text
React SPA
   ↓
Flask 单体 API
   ├─ 工时与团队管理
   ├─ 算法组统计数据源
   ├─ 绩效管理
   ├─ 知识库与 RAG
   ├─ AI 任务工作台
   └─ 专项任务管理（现场问题、需求池）
   ↓
MySQL 多业务库 + PostgreSQL pgvector + 文件工作区
   ↓
钉钉/Teambition API + 钉钉 MCP + 本地模型服务
```

## 2. 当前运行架构

### 2.1 表现层

- 主前端为 `frontend-react`，使用 React 单页应用承载登录、工时、绩效和 AI 页面。
- Flask 同时负责提供编译后的静态资源和 API。
- 仓库中仍保留旧 Vue 静态资源、旧 dashboard 路由和 Prototype 页面，形成多套入口并存。

### 2.2 API 与应用层

- Flask 通过 `/api/bt` Blueprint 集中注册业务路由。
- 路由实现分散在 `base`、`workhour`、`performance`、`ai` 等一级目录中。
- `base/route_registry` 负责统一注册，但人工维护的路由索引与实际路由已经存在偏差。
- 同一个 Flask 进程还承担 APScheduler 定时同步、后台线程、模型加载和静态文件服务。

### 2.3 数据层

| 数据库 | 所属业务 | 主要数据 |
|--------|----------|----------|
| `benti_management` | 本体工时与团队管理 | 开发任务、问题任务、明细、超期、用户、配置、锁、API 日志 |
| `algo_management` | 算法组统计数据源 | 算法任务及问题任务四张 A/B 表 |
| `perf_quarter_result` | 绩效管理 | 导航组、伺服/对接组季度绩效结果 |
| `kb_storage` | 知识库 | 目录节点、Markdown 正文、文本分块 |
| PostgreSQL pgvector | 知识库检索 | 文档分块向量 |
| `onsite_problem` | 现场问题 | 现场问题任务及明细 |
| `req_pool` | 需求池 | 需求任务及明细 |

开发环境支持 SQLite 回退，但生产环境使用多个独立数据库。

## 3. 六个主要业务域

### 3.1 工时与团队管理

职责包括：

- 本体项目 TB 单同步；
- 软件开发任务与问题任务管理；
- 有效工时、个人工时、团队详情；
- 工作日耗时统计；
- 增量更新、时间段更新和手动全量更新。

本体数据边界应当只包含导航组和伺服/对接组，不包含算法组。

### 3.2 算法组统计数据源

算法组拥有独立的 `algo_management` 数据库和四张任务表。

其业务边界是：

- 同步算法组两个项目的数据；
- 使用与本体一致的任务解析和工时统计口径；
- 只向“工作日耗时”业务提供统计数据；
- 不进入本体任务同步、个人工时、绩效等其他链路。

它更接近工作日耗时的独立数据源，而不是完整的前台业务系统。

### 3.3 绩效管理

职责包括：

- 季度绩效输入填充；
- 导航组与伺服/对接组绩效计算；
- 个人绩效结果和历史结果查询；
- 结合任务数据进行评分和汇总。

绩效数据已使用独立数据库，但服务代码仍与主应用共享进程和配置。

### 3.4 知识库与 RAG

职责包括：

- 钉钉 Wiki 空间与目录同步；
- ALIDOC Markdown 下载；
- 文档分块、向量生成和检索；
- 知识问答、任务分析和看板分析。

知识库同时依赖 MySQL 元数据、PostgreSQL pgvector、钉钉 Wiki API、钉钉 MCP 和本地 embedding/rerank 模型，是当前依赖链最长的业务域。

### 3.5 AI 任务工作台

职责包括：

- TB 任务上下文整理；
- AI 辅助分析；
- 任务草稿生成与编辑；
- Teambition 任务创建；
- ttyd/Claude 交互终端；
- 结合知识库生成分析和建议。

当前状态同时存放在数据库、用户文件工作区和前端状态中。

### 3.6 专项任务管理

包括两套相对独立的业务：

- 现场问题跟踪；
- 需求池管理。

两者都有独立数据库、同步逻辑和 API。后续如果继续扩展，应拆成两个明确的业务域，而不是继续放入 `base`。

## 4. 三个平台能力

### 4.1 身份、组织与权限

- 钉钉 OAuth 与免登；
- 本地登录；
- 用户、团队、角色；
- 页面和数据权限。

### 4.2 同步与外部集成

- access token 管理；
- 钉钉/Teambition API Client；
- MCP 调用；
- 增量、全量和专项同步；
- API 用量、限流、重试和更新锁；
- 定时任务。

### 4.3 配置与运行基础设施

- 项目、成员、字段 ID 和时间范围配置；
- 多数据库连接和初始化；
- 日志、runtime 文件与用户工作区；
- 前端构建、静态文件和部署脚本。

## 5. 当前主要架构问题

### 5.1 业务边界与目录边界不一致

`base` 同时包含认证、配置、任务同步、算法组、现场问题、需求池和统计逻辑，已经成为缺少明确职责的公共目录。

### 5.2 同步模块职责过重

`base/sync/task_sync.py` 同时承担：

- API 请求编排；
- 任务类型判断；
- 自定义字段解析；
- 数据过滤；
- A/B/C 表写入；
- 增量和全量流程；
- 重试、失败记录、锁和时间游标。

任何业务口径调整都可能影响多条同步链路。

### 5.3 进程职责过多

Flask 进程同时承担 HTTP、静态资源、定时同步、后台线程和模型服务。模块级“只启动一次”标记只能约束单进程，无法天然防止多 worker 重复调度。

### 5.4 数据库虽然拆分，所有权仍不清晰

多业务数据库已经物理隔离，但 ORM、初始化和迁移仍集中在主数据库模块中。算法组、现场问题和需求池依然通过主应用的公共模型体系管理。

### 5.5 全局配置产生业务耦合

`last_update_time`、`daily_sync_enabled` 和 API 限额被多类同步共享。一个业务推进时间游标或改变开关，可能影响另一个业务。

### 5.6 算法组隔离依赖调用方自觉

算法组只能用于工作日耗时，但当前缺少统一的数据访问边界。成员过滤散落在定时任务、同步服务和统计服务中，容易遗漏。

### 5.7 新旧入口并存

React、旧 Vue 静态资源、dashboard 兼容接口、Prototype 页面和旧注释代码同时存在，增加了判断真实入口的成本。

### 5.8 可观测性与运行控制混杂

API 用量统计、业务开关、自动限流和全量更新绕过机制耦合在同一个监控组件中。目前硬限还存在临时放大值，运行策略与文档配置不一致。

## 6. 建议的目标边界

建议后端逐步形成以下结构：

```text
backend/
  platform/
    auth/
    config/
    dingtalk/
    scheduling/
    observability/
    database/
  domains/
    workhour/
      benti/
      algorithm/
      statistics/
    performance/
    knowledge/
    ai_workspace/
    onsite_problem/
    requirement_pool/
  api/
    routes/
  scripts/
```

每个业务域内部至少区分：

- `routes`：HTTP 输入输出；
- `service`：业务用例编排；
- `repository`：数据库读写；
- `client`：外部 API；
- `models`：领域数据结构；
- `jobs`：定时任务入口。

## 7. 建议的重构顺序

1. **先拆本体同步**：将列表获取、明细获取、字段解析、持久化、增量/全量编排分开。
2. **建立成员范围策略**：本体、算法、绩效分别通过统一作用域获取成员，调用方不能自行查询全部用户。
3. **拆分同步游标**：TB、KB、现场问题、需求池各自拥有独立游标和开关。
4. **独立调度层**：定时任务从 Flask 应用初始化中移出，使用数据库锁保证单实例执行。
5. **整理知识库流水线**：明确目录扫描、增量判断、Markdown 下载、分块、向量更新五个阶段。
6. **清理遗留入口**：确认 React 为唯一前端后，逐步移除旧 Vue、dashboard 兼容入口和失效路由索引。
7. **最后统一 API 和配置**：按业务域建立稳定的 API 前缀、配置对象和运行状态接口。

## 8. 当前阶段约束

- 本文仅用于架构分析和后续重构规划。
- 当前工作区仍包含多组未提交修改，开始结构性重构前应先按业务主题拆分提交。
- 未经明确指令，不部署当前本地修改。
