# RAG v2：研发项目与模块知识助手设计

> 状态：产品与技术设计稿，待 canary 验证  
> 日期：2026-07-31  
> 适用范围：Management-System 的 RAG v2  
> 当前口径：文本与表格优先，不做全量多模态和源码级理解
> 当前实施顺序：[RAG v2 文档索引](./RAG-v2-00-文档索引.md)

## 1. 结论先行

RAG v2 不以“处理全部 55G 文档”为目标，而是服务两个明确用户：研发新员工和需要接手项目的工程师。

产品解决三个问题：

1. **人员与任务知识**：谁参与过什么项目，相关任务和方案在哪里；
2. **项目事实查询**：专项、订单项目有哪些时间节点、验收项和负责人；
3. **模块文档检索**：代码仓库中有哪些模块设计、接口、配置和版本说明。

一句话定位：

> 连接钉钉项目文档、TB 任务和代码仓库文档，为研发人员提供可检索、可汇总、可引用的项目与模块知识。

技术上采用“结构化查询 + Hybrid RAG”双通道：日期、负责人、状态和验收项走结构化查询；任务、方案和模块设计走关键词与向量混合检索。LLM 只负责理解问题和基于证据组织答案，不承担事实存储和精确计算。

## 2. 背景与当前事实

### 2.1 用户问题

研发知识分散在钉钉 Markdown、TB 任务和代码仓库文档中。现有搜索能找到含关键词的文件，但难以直接回答：

- 谁做过某个模块或类似任务；
- 某项目有哪些历史方案；
- 某专项或订单项目何时验收；
- 某项目还有哪些验收项；
- 某模块的设计和配置说明在哪里；
- 新员工接手项目应该先阅读哪些材料。

### 2.2 当前可核验状态

- 已有 Markdown 同步、文档解析和知识库存储链路；
- 已有 structured / meeting / table / text 四类切块；
- 已有 FULLTEXT/FTS、pgvector、RRF 和 Cross-Encoder reranker；
- legacy 26 题评测中，Recall@5 从 34.13% 提升到 59.60%，该结果只代表旧数据基线；
- 新数据曾统计约 55G，包含 5,427 份 Markdown 和 19,886 张图片；
- 当前工作区无法直接访问原始 Markdown 目录，因此本文不虚构新的类型占比、字段覆盖率或新评测结果。

## 3. 目标与非目标

### 3.1 V1 目标

- 从目标文档中可靠检索人员、项目、任务、方案、时间节点和验收信息；
- 支持项目、人员、开发组、模块、文档类型和时间范围筛选；
- 所有答案返回原始文档、仓库路径或 TB 任务链接；
- 能明确区分“文档提及”“参与”“负责人”等不同关系；
- 用新测试集验证数据解析、检索、事实提取和引用质量。

### 3.2 V1 非目标

- 不做全公司通用知识问答；
- 不处理全部 55G 文档；
- 不做全量图片 OCR、视觉摘要或多模态向量；
- 不做源码 AST、调用链、Git blame 或自动代码诊断；
- 不建设知识图谱数据库；
- 不使用多 Agent；
- 不预测项目延期或员工能力；
- 不自动修改项目状态、任务或代码；
- 不把检索结果当作唯一官方事实源。

## 4. 用户与核心场景

### 4.1 主要用户

| 用户 | 核心任务 | 期望结果 |
| --- | --- | --- |
| 研发新员工 | 理解项目、人员和模块 | 快速获得阅读入口和来源 |
| 项目接手工程师 | 查历史任务与方案 | 减少重复询问和重复设计 |
| 项目成员 | 查节点、验收项和负责人 | 得到可核对的项目事实 |

### 4.2 场景一：人员与任务知识

典型问题：

- 谁参与过二维码定位相关任务？
- 某人做过哪些导航模块工作？
- 导航组有哪些到点精度相关方案？
- 某个版本修改由哪些任务推动？

回答必须区分：

- `mentioned`：仅在文档中被提及；
- `participant`：上下文明确表达参与；
- `owner`：上下文或结构化字段明确表达负责；
- `author`：文档或提交元数据显示作者。

`@某人` 本身只能生成 `mentioned` 候选，不能自动认定为负责人。

### 4.3 场景二：项目节点与验收

典型问题：

- 某订单项目计划什么时候验收？
- 下个月有哪些项目到达关键节点？
- 某专项还有哪些验收项未完成？
- 两份项目文档的验收日期是否冲突？

日期、状态、负责人和验收项优先从结构化事实表查询；RAG 用于解释项目背景、方案内容和验收要求。

### 4.4 场景三：模块设计文档

V1 只接入代码仓库中的文档资产：

- `README.md`；
- `docs/` 下的设计文档；
- 模块、接口和配置说明；
- 部署与使用说明；
- Changelog 和版本说明。

典型问题：

- 某模块解决什么问题？
- 某功能有哪些设计文档？
- 某项目涉及哪些模块？
- 当前说明文档对应哪个仓库和 commit？

## 5. 数据范围与准入规则

### 5.1 V1 纳入

- 指定开发组的任务与方案文档；
- 专项和订单项目文档；
- 项目节点与验收表；
- 与上述项目关联的 TB 任务；
- 白名单代码仓库中的 Markdown 文档。

### 5.2 V1 暂不纳入

- 与研发项目无关的行政和泛知识文档；
- 主要信息只存在于图片中的文档；
- 无法确定权限或来源的文档；
- 无正文、重复导出或明显失效的文档；
- 代码仓库中的源码、二进制和构建产物。

### 5.3 准入判断

文档满足以下任一条件即可进入 canary 候选集：

- 标题、目录或正文明确包含目标项目/开发组；
- 存在任务、方案、负责人、节点或验收结构；
- 是目标仓库的设计或说明文档；
- 被真实用户问题或 TB 任务引用。

所有准入原因记录为元数据，避免凭主观感觉挑选“容易回答”的文档。

## 6. Markdown 高阶分析设计

这里的“高阶分析”不是训练复杂模型，而是在文档级建立可解释的数据画像和事实候选。

### 6.1 结构画像

对每份 Markdown 统计：

| 维度 | 分析内容 | 产品用途 |
| --- | --- | --- |
| 基础规模 | 字符、token、段落、标题层级 | 决定切块策略 |
| 内容结构 | 列表、表格、代码块、链接、图片 | 判断解析风险 |
| 标题路径 | 项目、任务、方案、验收等章节 | 增强召回和引用 |
| 图片依赖 | 图片数量、图片附近文本 | 标记 V1 覆盖缺口 |
| 外部链接 | TB、钉钉、Git 仓库链接 | 建立来源回链 |

产出：`document_profile`，不直接生成用户结论。

### 6.2 文档类型识别

优先使用目录、标题和结构规则识别：

- `task`：任务说明、任务背景、任务产出；
- `design`：方案、设计、技术说明；
- `project`：专项或订单项目；
- `acceptance`：验收表、验收标准；
- `module_doc`：模块、接口、配置、部署说明；
- `other`：暂不进入 V1 核心检索。

规则无法判断时标记 `unknown`，canary 阶段人工复核；不为了分类而引入新的分类模型。

### 6.3 显式实体提取

提取以下实体候选：

- 人员：`@人员`、负责人、执行人、作者；
- 组织：开发组、项目组；
- 项目：专项、订单项目名称；
- 任务：任务标题、TB 链接或任务 ID；
- 模块：仓库名、模块名、包名；
- 时间：计划时间、实际时间、验收时间；
- 状态：未开始、进行中、完成、验收中等；
- 验收项：验收内容、标准和结果。

人员优先通过已有员工目录做别名归一；项目和模块通过白名单词表归一。没有明确上下文时只保存候选，不生成强关系。

### 6.4 显式关系提取

V1 只提取原文能够直接支持的关系：

```text
人员 --mentioned/participant/owner/author--> 任务或文档
任务 --belongs_to--> 项目
方案 --supports--> 任务或项目
项目 --has_milestone--> 时间节点
项目 --has_acceptance_item--> 验收项
项目 --touches--> 模块
模块文档 --belongs_to--> 仓库/模块/commit
```

关系必须保存原文片段和来源位置。V1 不做多跳推理，也不把共现直接当因果关系。

### 6.5 时间与状态归一

日期统一为 ISO 日期，并同时保留原始文本。处理范围：

- `YYYY-MM-DD`、`YYYY/MM/DD` 和常见中文年月日；
- “计划/实际/验收/发布时间”等日期角色；
- 项目状态和验收状态。

“下周、月底、尽快”等相对时间不自动换算为正式节点，只标记为模糊时间并返回原文。

### 6.6 质量与冲突分析

使用简单规则生成提示，不自动裁决：

- 同一项目存在多个验收日期；
- 同一任务出现多个明确负责人；
- 文档超过设定时间未更新；
- 标题相同或正文高度重复；
- 文档只有图片、正文不足；
- 文档状态与时间节点可能矛盾；
- 仓库文档来自非默认分支或旧 commit。

输出统一使用“可能冲突”“待确认”，不由 LLM 自动修改事实。

### 6.7 可回答性分析

将真实问题映射到所需字段：

| 问题类型 | 必要数据 | 缺失时行为 |
| --- | --- | --- |
| 谁做过什么 | 人员关系、任务/方案 | 返回提及记录，不推断负责 |
| 项目何时验收 | 项目、验收日期、来源 | 明确数据不足 |
| 有哪些历史方案 | 项目/模块、design 文档 | 返回检索结果与引用 |
| 模块如何设计 | 仓库、模块文档、commit | 返回文档，不分析源码 |

通过“能回答/部分回答/不能回答”统计决定后续补数据，而不是默认增加模型复杂度。

## 7. 数据模型

在现有 `kb_documents`、`kb_chunks` 和 pgvector 基础上扩展，不引入图数据库。

### 7.1 文档元数据

建议为文档增加元数据字段或独立元数据表：

```text
source_type       dingtalk / tb / git_doc
document_type     task / design / project / acceptance / module_doc
project_names     JSON
team_names        JSON
module_names      JSON
people_mentions   JSON
source_url
repo_name
repo_path
branch
commit_hash
source_modified_at
content_hash
parser_version
```

### 7.2 事实表

使用一张简单事实表保存需要精确查询的内容：

```text
fact_id
document_id
fact_type         person_relation / milestone / acceptance_item / project_module
subject
predicate
object
normalized_value
evidence_text
source_location
confidence        rule_confirmed / human_confirmed / candidate
updated_at
```

`confidence` 表示提取状态，不表示模型对根因的概率。

## 8. 解析与切块

### 8.1 解析原则

- 原始 Markdown 作为事实源，`raw_json` 仅用于审计；
- 保留标题路径、列表层级、表头、链接和 `@人员` 上下文；
- HTML 只保留可见文本与结构，不保留样式；
- 图片保留 URL、所在章节和相邻文本，不做视觉理解；
- Git 文档保留仓库、路径、分支和 commit。

### 8.2 切块策略

复用现有四类切块，V1 重点修正两处：

1. 每个 chunk 注入短标题路径、项目、模块和文档类型；
2. 表格按行组切分并重复表头，禁止把一行拆开。

canary 中对比两组参数，不提前宣称最优：

- Baseline：现有切块参数；
- Candidate：较小的章节/行组块，并保留相邻上下文。

最终参数以新测试集的 Recall@5、MRR 和 nDCG@5 决定。

## 9. 查询与检索路线

### 9.1 查询分类

使用可解释的关键词和字段规则先路由；不引入 Agent：

| 查询 | 路线 |
| --- | --- |
| 谁、负责人、参与 | 人员事实 + 文档检索 |
| 时间、节点、验收、状态 | 结构化事实查询 |
| 方案、设计、说明、如何 | Hybrid RAG |
| 混合问题 | 两路并行后统一生成 |

无法稳定分类时同时执行结构化查询和 Hybrid RAG，由回答层去重，不需要自主规划循环。

### 9.2 Hybrid RAG

复用现有链路：

```text
关键词/FULLTEXT召回
        +
pgvector向量召回
        ↓
      RRF融合
        ↓
bge-reranker-base重排
        ↓
返回文档片段、标题路径和来源
```

关键词检索负责人员、项目名、模块名和版本号等精确词；向量检索负责同义表达；reranker 负责重新判断问题与候选片段的相关性。

### 9.3 回答约束

回答必须：

- 区分事实、文档提及和系统推断；
- 引用原文标题、链接或 Git 路径；
- 项目事实显示文档更新时间；
- 多来源冲突时并列展示，不自动选择；
- 没有证据时明确回答“当前知识库未找到”；
- 不根据 `@人员` 自动生成绩效或能力评价。

## 10. 产品功能

### 10.1 V1

- 统一搜索与带来源问答；
- 项目知识卡：人员、任务、方案、节点、验收项；
- 人员经验卡：提及、参与、负责、作者分开展示；
- 项目节点与验收查询；
- 模块文档检索；
- 项目交接摘要；
- 无答案、过期和关系错误反馈。

### 10.2 后续候选

- 相关任务和方案推荐；
- 文档冲突与过期提示；
- 基于已检索材料生成 TB 任务草稿。

是否建设由真实问题和反馈决定，不作为 V1 完成条件。

## 11. 评测设计

### 11.1 Canary

从目标范围抽取 100—200 份代表性文档：

- 覆盖任务、方案、项目、验收和模块文档；
- 覆盖普通正文、列表和表格；
- 同时包含短文档、长文档、重复文档和信息不足文档；
- 测试题来自真实查询，不根据已选文档反向编造容易命中的问题。

### 11.2 新测试集

计划建立 40 题，具体数量可根据有效真实问题调整：

| 类型 | 主要验证 |
| --- | --- |
| 人员—任务关系 | 关系标签与目标文档召回 |
| 任务—方案检索 | 语义召回与排序 |
| 项目节点—验收 | 字段提取与精确回答 |
| 模块文档 | 仓库文档召回与版本引用 |
| 无答案/冲突 | 拒答与冲突展示 |

### 11.3 指标

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 解析 | 文档成功率、表格完整率 | 文档能否进入后续链路 |
| 提取 | 人员关系、日期、验收项准确率 | 人工抽样复核 |
| 检索 | Recall@5、MRR、nDCG@5 | 与 legacy 口径一致但数据集独立 |
| 回答 | 引用正确率、事实一致率、拒答准确率 | 不用单一主观分数 |
| 产品 | 查询完成时间、来源点击、问题解决反馈 | 上线后再采集 |

新数据尚未评测前，不使用 legacy 的 `34.13% → 59.60%` 作为 RAG v2 结果。

## 12. 实施路线

### Phase 0：数据审计

- 生成文档结构画像；
- 统计目标文档类型、字段覆盖和图片依赖；
- 建立白名单和 canary 集；
- 人工复核实体与关系规则。

### Phase 1：文本与表格 canary

- 接入目标钉钉 Markdown 和 TB 数据；
- 扩展元数据与事实表；
- 修正标题路径、`@人员` 和表格行组；
- 跑通结构化查询与 Hybrid RAG。

### Phase 2：仓库文档

- 白名单同步 README 和 docs；
- 保存仓库、路径、分支和 commit；
- 建立模块文档测试题。

### Phase 3：评测与范围决策

- 对比 baseline 与 candidate；
- 分析 Bad Case 属于数据、解析、召回、排序还是生成；
- 只有图片缺失成为主要问题时，才评估 OCR 或多模态。

## 13. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| `@人员` 被误判为负责人 | 关系分级，展示证据原文 |
| 时间与状态过期 | 展示来源和更新时间，不声称实时 |
| 多文档互相冲突 | 并列展示并标记待确认 |
| 只挑容易命中的文档 | 测试题来自真实问题，保留无答案题 |
| 权限泄露 | 所有召回通道先做 ACL 过滤 |
| 仓库文档与代码版本不一致 | 保存 branch 与 commit，不分析源码 |
| 图片承载关键信息 | 标记覆盖缺口并返回原图链接 |
| LLM 编造关系或日期 | 精确事实来自事实表，答案必须引用 |

## 14. Interview 统一口径

### 14.1 为什么不处理全部 55G？

数据规模不是产品目标。V1 先围绕人员经验、项目节点、验收和模块文档建立可验证闭环，再根据未回答问题扩展数据范围。

### 14.2 为什么暂时不做图片？

首批核心问题主要依赖文本和表格。图片在 V1 保留回链；只有评测证明图片缺失是主要瓶颈时，才投入 OCR 或多模态。

### 14.3 为什么不只用钉钉搜索？

当前工作方式下，原生搜索主要返回包含关键词的文档，难以跨任务、项目和仓库文档回答语义问题，并汇总时间节点与验收项。本系统仍返回原文供用户核验。

### 14.4 为什么既有 RAG 又有结构化查询？

方案和任务适合语义检索；日期、状态和验收项要求精确，使用结构化查询更可靠。产品不强迫所有问题都走向量检索。

### 14.5 接入代码仓库是否代表能理解源码？

不是。V1 只接入仓库中的 README、设计、接口、配置和版本文档；源码级理解和代码诊断不在范围内。

### 14.6 当前取得了什么结果？

legacy 数据上完成过检索评测，Recall@5 从 34.13% 提升到 59.60%。RAG v2 当前是范围重定义和 canary 设计阶段，新数据上的结果必须重新评测。
