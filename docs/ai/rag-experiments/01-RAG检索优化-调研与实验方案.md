# RAG 检索优化：主流方案调研与对照实验

> 日期：2026-06-29  
> 状态：三版实验完成。v3（base, 59.6%, 服务器 ~1s）为推荐方案

---

## 第一部分：主流 RAG 方案调研

### 1. 分块策略（Chunking）

| 策略 | 原理 | 优势 | 劣势 | 适用场景 |
|------|------|------|------|---------|
| **固定窗口** | 按固定 token 数滑动切分，相邻窗口重叠 | 实现简单、通用性强 | 语义割裂，段落易被截断 | 纯文本、无结构文档 |
| **语义分块** | 相邻句子 embedding 相似度断崖处切分 | 语义连贯性好 | 依赖 embedding 质量，切点不稳定 | 散文、博客 |
| **层级分块** | 按 `##`/`###` 标题层级切，保留父子结构 | 技术文档最优，章节完整 | 依赖文档有规范标题 | 技术文档、API 文档 |
| **小大块策略** | 检索用小块 + 生成用大块，两套索引 | 兼顾精度和完整度 | 存储翻倍 | 高精度场景 |
| **命题分块** | LLM 重写每段落为独立命题后索引 | 检索精度最高 | LLM 调用贵、延迟大 | 不推荐 |

**我们的选择：4 策略自适应分块**，按文档类型自动选策略：

| 文档类型 | 策略 | 粒度 |
|---------|------|------|
| 技术文档（有 `##` 层级） | 层级分块 | 800-1000 token |
| 会议纪要/周报 | 段落聚合 | 500-800 token |
| 表格（.axls） | 行分组 + 表头前缀 | 20-30 行/片 |
| 其他 | 固定窗口 | 800 token，150 重叠 |

每个切片注入元数据（文档路径 + 章节标题 + 知识库来源），多数开源方案未做到。

### 2. 嵌入模型（Embedding）

| 模型 | 维度 | 中文效果 | 大小 | 特点 |
|------|------|---------|------|------|
| **bge-small-zh-v1.5** | 512d | 一般 | ~100MB | 轻量 CPU 友好，当前基线 |
| **bge-large-zh-v1.5** | 1024d | 好 | ~1.3GB | 中小部署甜点 |
| **bge-m3** | 1024d | 最优 | ~2.2GB | dense+sparse 合一，单模型替代"向量+BM25" |
| **text-embedding-3-small** | 1536d | 好 | API | 无需本地 GPU |
| **GTE-Qwen2** | 768-4096d | 极优 | 大 | 2024 SOTA，极致精度 |

### 3. 检索策略（Retrieval）

| 策略 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **纯关键词（BM25）** | TF-IDF 词频匹配 | 专有名词精确匹配 | 无语义泛化 |
| **纯向量** | embedding 余弦相似度 | 语义泛化强 | 专有名词可能漏 |
| **混合检索（Hybrid）** | 关键词 + 向量 → RRF 融合 | **互补优势，工业界主流** | 融合权重调试 |
| **多路召回** | 多 embedding 模型同时检索 | 覆盖更全 | 延迟翻倍 |
| **HyDE** | LLM 生成假设答案 → 用答案检索 | 缩小语义鸿沟 | 多一次 LLM 调用 |

**我们的选择：Hybrid RRF 融合**（FTS + bge-small 向量 → RRF k=60），架构合理，bge-small 本身是瓶颈。

---

### 4. 重排策略（Reranking）

检索阶段追求**快**（从数千 chunks 召回 20 个候选），允许不精确。重排阶段追求**准**（对 20 个候选精细打分，取 top-8 进 prompt）。

| 方案 | 原理 | 精度 | 单对延迟 | 适用 |
|------|------|------|---------|------|
| **无重排** | 只靠检索排序 | 基础 | 0ms | 当前现状 |
| **Cross-Encoder 重排** | 对每个 query-chunk 对精细打分 | 高 | ~50ms | **性价比最高** |
| **LLM-as-Reranker** | LLM 判断 query-chunk 相关性 | 最高 | ~500ms | 太贵 |
| **Cohere Rerank** | 托管 API 重排 | 高 | API 延迟 | 外部依赖 |

**Cross-Encoder 重排是最大单点优化**。业界数据：加入后 Recall@5 提升 5-15 个百分点。

---

### 5. 全景差距

| 环节 | 业界主流 | 我们现状 | 差距 |
|------|---------|---------|------|
| 分块 | 固定窗口 / 层级分块 | 4 策略自适应 + 元数据 | ⭐⭐⭐⭐ 已到位 |
| 嵌入 | bge-m3 / OpenAI ada | bge-small | ⚠️ 精度有限 |
| 检索 | Hybrid RRF | Hybrid RRF | ⭐⭐⭐ 合理 |
| 重排 | Cross-Encoder | **无** | ❌ 最大短板 |
| 评测 | Recall@K / MRR / nDCG | **无指标** | ❌ 黑盒 |

### 3. 评估指标

| 指标 | 含义 | 说明 |
|------|------|------|
| **Recall@5** | 前 5 条命中正确答案的比例 | `|top5 ∩ relevant| / |relevant|` |
| **MRR** | 第一个正确答案排名的倒数均值 | `(1/rank₁ + …)/N`，越近 1 越好 |
| **nDCG@5** | 考虑排名的综合相关性评分 | 排名靠前得分高，归一化到 0-1 |

支持按查询类型（技术文档/会议/表格/跨文档）出细分表。

### 4. 测试集：TREC Pooling + LLM-as-Judge

**为什么用 Pooling**：单系统检索有偏见——它搜不到的不代表不相关。TREC/BEIR 等学术基准的做法是合并多系统结果形成候选池。

**构建流程**：

```
对每道题：
  1. 三路检索各取 top-15（FTS 关键词 + 向量语义 + Hybrid 混合）
  2. 结果合并去重 → 候选池（约 30-40 条）
  3. 候选池内容 + 题目 → deepseek-v4-pro (temperature=0)
  4. LLM 返回 {"relevant_ids": [...]} → 写入 relevant_chunk_ids
```

**为何不用 RAGAS 自动生成**：RAGAS 从文档自动生成 `<问题, 答案>` 对虽然全自动，但生成的 query 往往"太像文档原文"，检索系统天然容易命中，评估区分度不够；且无法覆盖真实用户提问方式。因此选择"人工出题 + LLM 标注"混合方案：出题贴近业务场景，标注交给 LLM 提效。

**质量保障**：
- 每道题 Pooling 三路检索确保候选池无偏见
- LLM 标注 temperature=0 确保结果一致
- 标注后抽检 20% 人工验证
- 空标注题目 → 重新标注 → 仍空则换题

详细方法见 [`02-how-to-build-testset.md`](./02-how-to-build-testset.md)。

| 参数 | 值 |
|------|-----|
| 三路各自 top-k | 15 |
| 标注 LLM | deepseek-v4-pro |
| 测试题 | 26 条 |
| 覆盖类型 | 技术文档(10) / 会议纪要(7) / 表格(4) / 跨文档(5) |
| 难度分布 | easy(6) / medium(12) / hard(8) |

#### 已知问题

**问题 1：Hybrid RRF 融合稀释向量检索好结果** ⚠️ 已验证，双路召回非最优解

以 #24（自学习计算方法替换实验）为例：

| 检索方式 | chunk 1224 排名 |
|----------|-----------------|
| FTS 关键词 | 不在 top-20（chunk 用词与 query 术语差异大） |
| 向量语义 | **#15** ✅ |
| Hybrid RRF (k=60) | **#35** ❌ |

**根因**：query 使用"计算方法替换实验"、"对比方案"，chunk 使用"批量仿真"、"滑动窗口/welford/shrinkage"，FTS 匹配不到。RRF 融合时 FTS 的差排名拖累了向量侧的好结果。

**v2 双路召回尝试**：Hybrid + 纯向量各 top-20 合并。chunk 1224 确实进入了候选池，但 **reranker 未将其排入 top-5**（被同文档其他 chunk 竞争，或 600 字符截断丢失了对比信息）。同时双路引入的额外候选造成噪音，整体 Recall 从 63.3% 降到 60.0%。

**当前结论**：v3 单路方案（Hybrid RRF + base）为推荐配置。RRF 稀释是真实问题，但双路召回不是正确解法（噪音反噬精度）。后续可尝试：RRF k 值调优，或 chunk 级别内容质量提升。

**问题 2：reranker 延迟异常（单题 ~38s）** ✅ 已修复，持续优化中

**现象**：Strategy B 每道题 ~38s，远超预期的 ~100ms。

**诊断过程**：

| 步骤 | 排查 | 结论 |
|------|------|------|
| 怀疑 chunk 太长 | 截取 600 字符 | 无效，仍 38s+ |
| Profile 各环节 | hybrid 检索 5s / compute_score 38s | 瓶颈在 reranker |
| 对比 GPU vs CPU | P1000 GPU: 1.35s/对 / **CPU: 0.54s/对** | CPU 快 2.5x |
| 测试不同内容长度 | 截断 600 字 vs 全文 1060 字 | 13.9s vs 19.1s（10对） |

**根因**：Quadro P1000（4GB VRAM, 640 CUDA 核心）承载 2.2GB reranker 模型时推理极慢。本地 CPU 和服务器 CPU（i7-11700）均比 P1000 快。

**修复**：本地切 CPU（`use_fp16=False, device="cpu"`），换小模型 base（280MB）。

**服务器**：i7-11700 + base = 45ms/对, ~1s/query，生产可用。v2-m3 备选（160ms/对, ~2-3s, +3.7pp）。

**问题 3：自学习类文档 chunk 覆盖不足**

#24 和 #26 均涉及"自学习"相关文档（`【5】自学习计算方法替换实验.adoc`、`到点自学习实施效率优化.adoc`）。LLM 标注的相关 chunk 分别只有 1 条和 2 条，且检索均无法命中。可能原因：文档分块过碎或向量表示质量不足以捕获计算方法的语义相似性。

**问题 4：表格类检索 MRR 微降**

表格类型唯一 MRR 下降（-0.050）。表格信息密度高，关键词匹配本身效果尚可，重排可能将原本排在前面的正确 chunk 换到后面。说明对表格类文档，reranker 的语义理解优势不明显。

## 第三部分：模型决策树与重排策略引入

### 1. 嵌入模型决策树

```
需要零部署、CPU 友好？
├── 是 → bge-small-zh-v1.5（当前基线）
└── 否 → 追求精度？
          ├── 是 → GPU/大内存？
          │         ├── 是 → bge-m3（dense+sparse 合一，最优）
          │         └── 否 → bge-large-zh-v1.5
          └── 否 → 多语言？→ bge-m3
                  否 → 维持 bge-small
```

### 2. 重排策略决策树

实验发现：Hybrid RRF 在关键词与向量分歧大时会稀释向量好结果（chunk 1224：向量排 #15 → RRF 后 #35），导致 reranker 无米之炊。因此采用**双路召回 + 精排**范式。

```
用户提问
    ↓
┌───────────────────────────────────┐
│          双路召回                   │
│  Hybrid RRF top-N   纯向量 top-N  │
│       ↓                  ↓        │
│       └──── 合并去重 ────┘        │
│          候选池 ~30-40            │
└───────────────────────────────────┘
    ↓
候选数 ≤ 5？
├── 是 → 直接进 prompt（不重排，省延迟）
└── 否 → Cross-Encoder 重排（bge-reranker-v2-m3）
           ↓
        按 rerank 分数排序 → top-8 → prompt
```

**为什么双路召回？**

- Hybrid RRF 优势：关键词 + 语义互补，多数情况下排序质量好
- Hybrid RRF 缺陷：当 FTS 完全失败时，RRF 会拖累向量侧的好结果
- 纯向量补路：独立走 pgvector，不受 RRF 影响，确保语义匹配的 chunk 必然进候选池
- 合并后由 reranker 统一评分——好的留下，差的过滤

### 3. 重排落地设计

```
当前流程（基线）：
  FTS + 向量 → RRF 融合 → top-8 → 注入 Prompt

引入重排后（生产）：
  ┌─ Hybrid RRF top-20 ─┐
  └─ 纯向量 top-20 ─────┘
           ↓
     合并去重 → ~30-40 候选
           ↓
  Cross-Encoder 精排打分
           ↓
     重排序 → top-8 → 注入 Prompt
```

**改动范围**：

| 文件 | 改动 |
|------|------|
| `retriever.py` | 新增 `search_with_rerank()` 函数，可选开关 |
| `embedder.py` | 新增 reranker 模型加载（`FlagReranker`） |
| `chat.py` | 调用可选的重排路径 |

**性能控制**：

- 双路召回：hybrid + 向量各取 20，合并去重约 30-40 候选
- 精排：对 ~35 对打分，额外延迟 ~100ms（含一次额外的向量检索 ~3ms）
- reranker 模型 ~2.2GB，与 embedding 模型分时加载，不额外占显存
- 通过配置开关控制是否启用，方便 A/B 对比
