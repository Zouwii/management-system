## 5 模块分析要求

### 1. 需求雷达 — 存量挖掘

从用户当前任务中提取 10 个核心技术/业务关键词（去重）。
为每个关键词生成 "一词三建议"：

| 建议类型 | 逻辑 | 说明 |
|---------|------|------|
| 存量挖掘 | 同父任务或同领域还有什么可做 | 基于该用户已有的任务，找延伸方向，建议申报指派型工时 |
| 质量升维 | 当前任务如何做深做透 | 基于该用户已完成/进行中的任务，找补强点，建议申报自主型工时 |
| 前瞻探索 | 这个方向的前沿延伸 | 结合知识库规范和技术趋势，给出学习方向，建议申报能力型工时 |

格式:
{
  "keywords": [
    {
      "word": "关键词",
      "frequency": N,
      "suggestions": {
        "dig_deeper": "存量挖掘建议",
        "quality_up": "质量升维建议",
        "look_forward": "前瞻探索建议"
      }
    }
  ]
}

### 2. 自主型建议 — 增量改进

从用户现有任务中发现可以转化为自主型工时的工作内容。
依据 tb_rule：自主型工时必须基于实际问题、有明确可复用的产出物。

判定标准：
- 产品或项目问题复盘与改进方案
- 技术债识别、清理与重构
- 文档缺失补齐、规范梳理
- 工具脚本、自动化能力建设
- 性能、稳定性、可靠性优化
- 研发流程或协作效率改进

以下情况不计入有效工时：无明确问题来源、无产出或产出不可复用。

格式:
{
  "suggestions": [
    {
      "source_task": "引用的任务名",
      "problem": "发现的问题",
      "action": "改进建议和产出要求",
      "effort_days": 预估人天
    }
  ]
}

### 3. 能力型建议 — 学习储备

识别用户技术方向中的空白，给出学习建议。
依据 tb_rule：学习行为必须形成沉淀（文档 / 分享 / 结论），否则不计入有效工时；设上限 10-15%。

判定标准：
- 技术学习与笔记、技术分享准备
- 方案调研、Demo / PoC 验证
- 必须明确产出：文档/分享/结论

格式:
{
  "suggestions": [
    {
      "direction": "学习方向",
      "reason": "为什么需要学",
      "output_required": "强制产出（笔记/PPT/调研报告/Demo）",
      "effort_days": 预估人天
    }
  ]
}

### 4. 任务分布与风险分析

当前工时类型分布为：{ratio_stats}
依据 tb_rule 对标：指派型 50-60%、自主型 25-30%、能力型 10-15%。

基于任务数据识别风险：
- 结构性平庸：长期无自主型任务
- 交付真空：有任务无产出，创建中任务堆积
- 产出虚报：任务已标记完成但无工时填写
- 工时未填：任务在排期中但工时为 0

生成可复制的 TB 任务草案供下周使用。

格式:
{
  "ratio": {"assigned": 比例, "autonomous": 比例, "capability": 比例},
  "status": "合规 / 偏高 / 偏低",
  "detail": "分析说明",
  "alerts": [
    {"level": "red / yellow", "type": "风险类型", "description": "具体描述"}
  ],
  "draft_tasks": [
    {"title": "建议任务标题", "description": "任务描述"}
  ]
}
