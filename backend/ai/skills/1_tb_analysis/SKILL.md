## 5 模块分析要求

### 1. 需求雷达 — 存量挖掘

从用户当前任务中提取 10 个核心技术/业务关键词。
为每个关键词生成 "一词三建议"。每条建议必须引用具体的任务或知识库文档，不能泛泛而谈。

| 建议类型 | 数据来源 | 生成规则 |
|---------|---------|---------|
| 存量挖掘 | 兄弟任务 + 知识库 | 看同一父任务下还缺什么 + 知识库中相关的规范/方案建议补充什么，建议申报**指派型** |
| 质量升维 | 任务描述+产出 + 知识库 | 看当前产出是否符合规范 + 知识库中的标准/checklist要求了什么，建议申报**自主型** |
| 前瞻探索 | 知识库 | 结合知识库规范和技术趋势，给出该方向的**能力型**学习建议 |

**注意**: 
- 如果任务没有兄弟任务，存量挖掘应基于同领域的其他任务
- 如果知识库无相关内容，前瞻探索应基于技术常识给出合理方向
- 每条建议必须具体、可执行，直接引用任务名或文档名

格式:
{
  "keywords": [
    {
      "word": "关键词",
      "frequency": N,
      "suggestions": {
        "dig_deeper": "存量挖掘建议",
        "quality_up": "质量升维建议",
        "look_forward": "前瞻探索建议"
      }
    }
  ]
}

### 2. 自主型建议 — 增量改进

从用户现有任务中发现可以转化为自主型工时的工作内容。
依据 tb_rule：自主型工时必须基于实际问题、有明确可复用的产出物。
**至少生成 12 条建议，以下每类至少 2 条：**

判定标准：
- 产品或项目问题复盘与改进方案（≥2条）
- 技术债识别、清理与重构（≥2条）
- 文档缺失补齐、规范梳理（≥2条）
- 工具脚本、自动化能力建设（≥2条）
- 性能、稳定性、可靠性优化（≥2条）
- 研发流程或协作效率改进（≥2条）

以下情况不计入有效工时：无明确问题来源、无产出或产出不可复用。

格式:
{
  "suggestions": [
    {
      "source_task": "引用的任务名",
      "problem": "发现的问题",
      "action": "改进建议和产出要求",
      "priority_score": 1-10,
      "effort_days": 预估人天（1-2天）,
      "task_template": {
        "title": "任务标题（≤18字，可直接作为 TB 任务名）",
        "requirement_desc": "需求描述（1-3 句话说明背景和要解决的问题）",
        "outputs": ["产出描述1(N1天)", "产出描述2(N2天)"]
      }
    }
  ]
}

> **outputs 格式要求**：
> - 每条产出格式：`描述(N天)`，N 为小数
> - outputs 天数之和 = effort_days，且必须落在 [0.2, 0.5, 1.0, 1.5, 2.0, 2.5, 3.0] 之中
> - 2-5 条产出，按工作量拆分

### 3. 能力型建议 — 学习储备

识别用户技术方向中的空白，给出学习建议。
依据 tb_rule：学习行为必须形成沉淀（文档 / 分享 / 结论），否则不计入有效工时；设上限 10-15%。
**至少生成 12 条建议，以下每类至少 2 条：**

判定标准：
- 核心技术/框架深度学习（≥2条）
- 行业前沿方案调研与 PoC（≥2条）
- 技术分享/文档沉淀（≥2条）
- 工具链/基础设施优化调研（≥2条）
- 跨领域技能补全（≥2条）
- 代码规范/架构设计学习（≥2条）

格式:
{
  "suggestions": [
    {
      "direction": "学习方向",
      "reason": "为什么需要学",
      "output_required": "强制产出（笔记/PPT/调研报告/Demo）",
      "priority_score": 1-10,
      "effort_days": 预估人天（1-2天）,
      "task_template": {
        "title": "任务标题（≤18字，可直接作为 TB 任务名）",
        "requirement_desc": "需求描述（1-3 句话说明学习背景和目标）",
        "outputs": ["产出描述1(N1天)", "产出描述2(N2天)"]
      }
    }
  ]
}

> **outputs 格式要求**：
> - 每条产出格式：`描述(N天)`，N 为小数
> - outputs 天数之和 = effort_days，且必须落在 [0.2, 0.5, 1.0, 1.5, 2.0, 2.5, 3.0] 之中
> - 2-5 条产出，按工作量拆分

### 4. 任务分布与风险分析

**对标区间：指派型 50-60%、自主型 25-30%、能力型 10-15%**
**当前分布：{ratio_stats}**
**预期 vs 实际：{expected_vs_actual}**

detail 两端各 ≤ 100 字：

【任务分布】写各类型占比与对标区间的关系（偏高/偏低/缺失），结合业务类型分布（从 task_distribution 获取）指出工时集中方向。示例："指派占比偏高，自主接近下限，能力型缺失。工时集中在研发和产品方向。"
【工时排布】写已排工时 vs 至今预期工时（从 expected_vs_actual 获取），超排/少排量，完成率与时间进度偏差。一句总结。示例："已排超出预期 3d，完成率 56% 落后时间进度 60%，交付压力较大。"

alerts：偏差 ≥ 8% 才写结构偏差；进行中任务工时 ≥ 50% 才写交付风险。description ≤ 15 字。

格式:
{
  "ratio": {"assigned": 比例, "autonomous": 比例, "capability": 比例},
  "status": "合规 / 偏高 / 偏低",
  "detail": "【任务分布】\\n20字以内\\n\\n【工时排布】\\n20字以内",
  "alerts": [
    {"level": "red / yellow", "type": "逾期/结构偏差/交付风险", "description": "≤15字"}
  ],
  "draft_tasks": []
}
