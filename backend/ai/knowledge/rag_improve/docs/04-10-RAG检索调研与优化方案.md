## 一、当前状态：我们有什么

### 1.1 检索链路

```
用户问题 → Embedding（bge-small-zh-v1.5, 512d）
         → FTS5 全文索引（BM25）
         → RRF 融合（k=60）
         → 返回 top-8 chunks
         → 注入 Prompt → LLM 生成
```

### 1.2 各环节现状

| 环节 | 方案 | 评价 |
|------|------|------|
| 文档同步 | 钉钉 API → markdown → SQLite | ✅ 成熟，9 个知识库完整缓存 |
| 文档分块 | 4 策略自适应（structured/meeting/table/text） | ✅ 设计合理，语义完整性好 |
| 嵌入模型 | `BAAI/bge-small-zh-v1.5`，512 维 | ⚠️ 轻量但精度有限 |
| 关键词检索 | SQLite FTS5（BM25） | ✅ 中文可用，零部署成本 |
| 向量检索 | pgvector cosine | ✅ 成熟稳定 |
| 融合排序 | RRF（Reciprocal Rank Fusion, k=60） | ✅ 工业标准 |
| 重排（Rerank） | **无** | ❌ 缺失——最大短板 |
| 检索评测 | **无量化指标** | ❌ 不知道 recall 多少 |

### 1.3 已有但未做的事

你已经设计了完整的对照试验方案（`13-rag-retrieval-benchmark.md`），覆盖 5 组策略 A-E，但**尚未执行**。当前 RAG 检索质量是一个黑盒——你不知道它好还是不好。

### 2.2 各环节主流方案对比

#### 分块策略

| 策略 | 原理 | 适用场景 | 你的现状 |
|------|------|---------|---------|
| 固定窗口 | 按 token 数切分，50-100 token 重叠 | 通用场景 | ✅ 已用（text 类型） |
| 语义分块 | 用 embedding 相似度找断点 | 散文、博客 | 🟡 未用 |
| 层级分块 | 按 ##/### 标题切，父子关系保留 | 技术文档 | ✅ 已用（structured 类型） |
| 小大块策略 | 检索用小块（精确），生成用大块（上下文完整） | 精细检索 | 🟡 未用 |
| 命题分块 | LLM 重写每个段落为独立命题 | 高精度场景 | ❌ 太贵，不必要 |

**你的现状**：4 策略自适应已经是业界中上水平。加分项是元数据注入（文档路径 + 章节标题），这个做得很好。

#### 嵌入模型

| 模型 | 维度 | 中文效果 | 资源需求 | 你的现状 |
|------|------|---------|---------|---------|
| bge-small-zh-v1.5 | 512d | 一般 | 100MB，CPU 友好 | ✅ 当前使用 |
| bge-large-zh-v1.5 | 1024d | 好 | 1.3GB | 🟡 实验组 E |
| bge-m3 | 1024d | 最优（多语言+稀疏+稠密合一） | 2.2GB | 🟡 实验组 C/D |
| text-embedding-3-small | 1536d | 好（API） | 云端调用 | 🟡 计划过 |
| mGTE / GTE-Qwen2 | 768-4096d | 极优（2024 SOTA） | 较大 | ❌ 未调研 |

**你的现状**：bge-small 是最轻量的选择，但也是精度最低的。中文技术文档场景下，bge-m3 或 bge-large 有明显提升空间。

#### 检索策略

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **纯关键词（BM25）** | TF-IDF 变体，词频匹配 | 精确匹配强、可解释 | 无语义理解 |
| **纯向量** | embedding 余弦相似度 | 语义理解强 | 漏专有名词 |
| **混合检索（Hybrid）** | 关键词 + 向量 → 融合 | 互补优势 | 融合权重难调 |
| **多路召回** | 多 embedding 模型多路检索 | 覆盖更全 | 延迟高 |
| **HyDE** | 先生成假设答案再检索 | 缩小语义鸿沟 | 多一次 LLM 调用 |

**你的现状**：单模型混合检索（bge-small + FTS5 + RRF），是工业界主流方案。但 bge-small 的语义能力是瓶颈。

#### 重排（Rerank）

| 方案 | 原理 | 精度 | 延迟 | 你的现状 |
|------|------|------|------|---------|
| 无重排 | 只靠检索排序 | 基础 | 0ms | ✅ 当前 |
| Cross-Encoder 重排 | 对 query-chunk 对做精细打分 | 高 | 每对 ~50ms | 🟡 实验组 B/D |
| LLM-as-Reranker | 用 LLM 判断相关性 | 最高 | 每对 ~500ms | ❌ 太贵 |
| Cohere Rerank API | 托管重排服务 | 高 | API 延迟 | ❌ 外部依赖 |

**你的现状**：**无重排是最大短板。** 检索召回 20 条，最终选 8 条进 prompt。如果没有精排，前 8 条里混入不相关 chunk 的概率很高。Cross-Encoder 重排是最具性价比的补充。

### 2.3 进阶范式简介

这些你暂时不需要实现，但面试时提到会加分：

| 范式 | 一句话 | 面试能说什么 |
|------|--------|------------|
| **Agentic RAG** | 不是一次检索，是 Agent 多步检索：先搜→不够→换个角度再搜→综合 | 「我们当前是单轮检索，后续可以升级为 Agentic RAG——Agent 自主判断检索是否充分，不充分就换关键词再搜」 |
| **Self-RAG** | LLM 在生成前先自检：检索到的内容相关吗？足够回答吗？ | 「Self-RAG 通过反思机制降低幻觉率——生成前先验证检索质量，不够就拒绝回答而非编造」 |
| **Graph RAG** | 用知识图谱替代向量检索，适合实体关系密集的场景 | 「知识库包括 PRD 和 FSD 的引用关系时，Graph RAG 比纯向量检索更适合——能顺着依赖链路召回」 |
| **Corrective RAG** | 检索后先评估质量，不够就触发 web search 或重写 query | 「对关键业务场景，可以加入检索质量评估节点，召回不足自动降级到 web 搜索或人工兜底」 |

## 三、差距分析：我们缺什么

### 3.1 已做到位的

| 能力 | 水平 | 说明 |
|------|------|------|
| 文档同步管线 | ⭐⭐⭐⭐⭐ | 钉钉 API → 解析 → SQLite，完整闭环，工业级 |
| 分块策略 | ⭐⭐⭐⭐ | 4 策略自适应 + 元数据注入，超过大部分开源项目 |
| 混合检索架构 | ⭐⭐⭐ | FTS5 + pgvector + RRF，架构合理 |
| 模块化设计 | ⭐⭐⭐⭐ | `chunker/embedder/retriever/chat` 分层清晰 |

### 3.2 需要补的

| 能力 | 差距 | 影响 | 优先级 |
|------|------|------|--------|
| **检索质量量化** | 无 Recall/MRR 等指标 | 不知道检索好不好，无法优化 | 🔴 P0 |
| **重排（Rerank）** | 检索后无精排 | 不相关 chunk 混入 prompt，LLM 回答质量下降 | 🔴 P0 |
| **嵌入模型** | bge-small 精度有限 | 语义检索召回不足 | 🟡 P1 |
| **HyDE / Query 重写** | 用户问题不一定是好的检索 query | 口语化问题检索效果差 | 🟢 P2 |
| **检索结果缓存** | 重复问题重复检索 | 浪费算力 | 🟢 P3 |

### 3.3 核心差距解读

**P0-1：检索质量量化**

你现在的 RAG 是一个**黑盒**。你不知道：
- 用户搜「导航算法流程」，理想的 chunk 是不是真的在前 5 条里？
- 哪些查询类型检索效果好？哪些差？
- bge-small 换 bge-m3 到底能提升多少？

没有指标，优化就是盲人摸象。对照试验方案已经设计好了，就差执行。

**P0-2：重排（Rerank）**

这是**性价比最高的单点优化**。逻辑很简单：

```
检索阶段（粗排）：从几千 chunks 里快速召回 20 个候选
   ↓ 这一步追求快，允许不精确
重排阶段（精排）：对 20 个候选做精细打分，排序后取 top-8
   ↓ 这一步追求准，20 个候选的量可以接受 Cross-Encoder 的延迟
```

加入重排后，最终进 prompt 的 8 个 chunk 的**相关性显著提升**。业界数据：Cross-Encoder 重排通常提升 Recall@5 5-15 个百分点。

## 四、推荐优化路线

### Phase 1：建立评测基线（立即，1 周）

做完对照试验方案（A-E 五组），产出量化结论。

**投入**：约 3 天  
**产出**：一份「当前 RAG 检索质量报告」——这是优化的方向盘  
**面试素材**：「我对 RAG 检索质量做了系统的 A/B 对照试验，构建了 30 条标注测试集，对比了 5 种策略组合。最终选型基于数据而非直觉。」

### Phase 2：单点优化（1-2 周，按试验结论选择）

根据 Phase 1 的结论，从以下选项中选 1-2 个执行：

| 优化项 | 预期提升 | 成本 |
|--------|---------|------|
| 加 Cross-Encoder 重排 | Recall@5 +5~15% | 1 天开发 + 每次查询多 50ms |
| 换 bge-m3 嵌入模型 | Recall@5 +5~10% | 重新编码全量 chunk，约 2-3h |
| 换 bge-large 嵌入模型 | Recall@5 +3~8% | 同上 |
| bge-m3 + 重排 叠加 | Recall@5 +10~20% | 两者成本叠加 |

**决策原则**：选性价比最高的组合，不追求绝对最优。bge-m3 的 2.2GB 对部署环境有要求，如果内存不足就退到 bge-large。

### Phase 3：Query 优化（按需，1 周）

| 优化项 | 原理 | 示例 |
|--------|------|------|
| Query 重写 | LLM 把口语问题转成检索友好的 query | 「车走偏了怎么回事」→ 「AGV 走偏 根因 编码器 轮速差」 |
| HyDE | 先让 LLM 生成一个假设答案，用答案做检索 | 提问 → LLM 生成假设回答 → 用回答做向量检索 |
| 多 Query 检索 | 一个用户问题生成 3 个不同角度的检索 query | 原始 + 同义改写 + 中文 → 英文 |

**建议**：Phase 2 效果不理想时再考虑，因为每次多一次 LLM 调用，增加延迟和成本。

### Phase 4：生产化（按需）

- 检索结果缓存（相同 query 不重复检索）
- A/B 测试框架（新策略上线前对比旧策略）
- 检索失败 case 自动收集（用户点踩 → 记录 query + 检索结果）

## 五、技术选型速查

### 嵌入模型决策树

```
需要零部署、CPU 友好？
  ├── 是 → bge-small-zh-v1.5（当前方案）
  └── 否 → 追求精度？
            ├── 是 → 有 GPU/大内存？
            │         ├── 是 → bge-m3（dense+sparse 合一，当前最优）
            │         └── 否 → bge-large-zh-v1.5
            └── 否 → 需要多语言？→ bge-m3
                      不用多语言？→ 维持 bge-small
```

### 重排方案决策树

```
需要重排吗？
  ├── 检索结果 ≤ 8 条 → 不需要，直接进 prompt
  └── 检索结果 > 8 条 → 候选多少？
            ├── ≤ 30 条 → Cross-Encoder 重排（bge-reranker-v2-m3）
            └── > 30 条 → 先用 bge-m3 dense 粗排到 20 条，再 Cross-Encoder 精排
```

### 你的场景参数

| 参数 | 当前值 | 建议值 |
|------|--------|--------|
| 向量检索 top-N | 20 | 维持 |
| 全文检索 top-N | 10 | 维持 |
| 融合后候选 | 约 15-20 | 重排前喂给 reranker |
| 最终 top-K | 8 | 维持（控制 prompt 长度） |
| 单片段 max token | 800 | 可适当提高到 1000（如果 prompt 窗口变大） |

## 六、面试素材：RAG 优化叙事

> 我在 management-system 中自研了一套 RAG 检索系统，用于企业知识库的语义问答。上线后我发现了两个问题：一是检索质量缺乏量化指标，二是缺少重排环节导致不相关片段混入最终结果。
>
> 我做了两件事情。第一，我构建了一个标注测试集——从真实用户查询中收集 30 条，覆盖技术文档、会议纪要、表格数据、跨文档四类场景，人工标注了每条查询的理想答案片段。我把这个测试集作为检索质量的量化基线。
>
> 第二，我设计了一个 5 组对照试验——基线（bge-small + Hybrid RRF）、基线加重排、换 bge-m3 嵌入模型、bge-m3 加重排、bge-large 全套。通过 Recall@5、MRR、nDCG@5 三项指标做横向对比。最终选择了 XX 方案，相比基线 recall 提升了 XX%。
>
> 这个选型过程的本质是 PM 的数据驱动决策——不是凭感觉选技术方案，是用可量化的指标说话。同时我也调研了 Agentic RAG、Self-RAG、Graph RAG 等进阶范式，为后续迭代做了技术储备。
